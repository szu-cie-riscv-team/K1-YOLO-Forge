# K1 YOLO 与 XSlim 调研

日期：2026-10-17。范围：本地三份模型静态检查、现有项目接口阅读、官方文档和源码核对。没有执行训练、XSlim 量化或 K1 性能测试。完整结构证据见 [reference-models.json](reference-models.json)。

## 1. 三份模型实物检查

下表 H×W 均来自 ONNX 输入张量，不按文件名猜测。

| 项目 | 高速 320×320 | 高速 192×320 | 官方 no_dfl |
|---|---|---|---|
| 文件 | yolov8n_320x320.q.onnx | yolov8n_192x320.q.onnx | yolov8n_no_dfl.q.onnx |
| 字节数 | 1,925,664 | 1,925,676 | 3,367,042 |
| 输入 | float32 [1,3,320,320] | float32 [1,3,192,320] | float32 [1,3,640,640] |
| opset / IR | 17 / 8 | 17 / 8 | 17 / 9 |
| Conv | 43 | 43 | 63 |
| LeakyRelu | 37，alpha=0.1 | 37，alpha=0.1 | 0 |
| Sigmoid / Mul | 3 / 0 | 3 / 0 | 60 / 57 |
| QuantizeLinear / DequantizeLinear | 93 / 136 | 93 / 136 | 220 / 283 |
| 输出数 | 9 | 9 | 9 |
| 原始 checker | PASS | PASS | FAIL：元数据键重复 |
| 工具元数据 | xquant 2.0.1 | xquant 2.0.1 | xslim 2.0.6 |

SHA-256：

```text
320×320  fcfd8d16a5e6a4b03c438d5b634c1c1f7d2449ab60eb3d328759aae4ae715b8e
192×320  d4bf61db2a0925a0126052212479ff5044b621b12c6793420e085d36ae6b5438
no_dfl   56fdce64c5e9d93d965b7fde95e58e5e75aa2b97fc8bd192a4cd2ff5aff63b5d
```

320×320 文件哈希与 `riscv/k1muse_project/docs/review/2026-10-12_k1_camera_yolo_performance.md` 中已经记录的板端模型相同。这是文件身份核对，未新增性能测量。

三者均为 float32 输入输出、内部 QDQ 量化；不能因为扩展名 `.q.onnx` 就将输入改成 int8。Resize 均为 nearest/asymmetric/floor，2 倍上采样。

九输出按 stride 8、16、32 排列，每个尺度为：

```text
box distribution: [1, 4*reg_max, H/stride, W/stride]，当前 reg_max=16
class score:      [1, C,         H/stride, W/stride]，当前 C=80
score summary:    [1, 1,         H/stride, W/stride]
```

框分布仍有 64 通道，三个模型图内都没有 Softmax。结合现有项目解码器，可以确认这里的 no_dfl 指图外执行 DFL 解码；不是取消 DFL 训练损失，也不是已经输出最终 xyxy 框。高速模型的 score summary 是类别求和后 Clip 到 [0,1]；官方模型没有该 Clip。该量不能直接当作独立训练的 objectness。

官方文件有 13 个元数据键各重复两次。仅在内存副本中去重后 checker 通过；原文件保持不变。新工程导出时应产生唯一元数据键，不把原始 checker 失败悄悄忽略为 PASS。

## 2. 如何理解高速模型

高速模型的 backbone/neck 明显不同于标准 YOLOv8n：卷积权重可见 16→32→64→96→128 等通道，多个节点含 `rbr_reparam`。这些证据提示采用了重参数化模块的部署结构，但仅凭节点命名不能断言训练源码、确切模型家族或完整训练配置。

因此分两条路线：

1. 标准 YOLOv8n：使用可追溯的官方训练实现，导出九输出，建立精度与 K1 性能基线。
2. 高速兼容结构：继续定位其原始可训练结构/FP32 checkpoint；若无法找到，依据图拓扑实现对应部署结构，再验证 PyTorch→ONNX 数值一致性和训练效果。

不能将标准模型的 SiLU 直接换为 LeakyReLU，就声称复现了参考模型。量化 ONNX 也不包含优化器、原始浮点权重和训练期多分支，无法完整逆推出 epochs、学习率、增强和训练配方。去量化只得到近似权重。

192×320 的输入像素数是 320×320 的 60%，有潜在速度收益；实际收益受拓扑、内存、EP 划分和前后处理影响。它对 4:3 相机图像的缩放比例也不同，可能降低小目标精度，需要单独评估。

## 3. K1 的算子与版本约束

官方快速入门使用 YOLOv8 ONNX opset 17；三个实物也都是 17，因此首条兼容路线选择 17、静态 batch=1、固定 H/W，并在模型外做 DFL/NMS。[官方快速入门](https://github.com/spacemit-com/docs-ai/blob/main/zh/compute_stack/ai_compute_stack/quick_start.md)

算子名出现在支持表中只是必要线索，还应检查 domain、输入类型、属性、常量条件和 QDQ 位置。例如 Conv 的 kernel_shape 及常量权重条件、Resize 的 mode/坐标模式都会影响 EP 接管。当前文档是持续更新的，不能将其列出的 opset 数字机械地解释成所有历史 runtime 的最小或最大支持版本。[EP 算子说明](https://github.com/spacemit-com/docs-ai/blob/main/zh/compute_stack/ai_compute_stack/onnxruntime_ep_ops.md)

验收需要同时覆盖：

- 静态检查：opset/IR/domain、输入输出、类别数、Conv/Resize 属性、QDQ 和元数据。
- 数值检查：PyTorch 与 FP32 ONNX，以及 FP32 与量化模型的检测结果。
- 板端检查：实际 SpaceMIT EP 初始化、主要卷积进入 EP、子图划分及回退耗时。

CPU 负责外部后处理可以是预期设计；需要排查的是耗时网络主体意外回退。官方提供 `SPACEMIT_EP_DUMP_SUBGRAPHS` 和 `SPACEMIT_EP_DEBUG_PROFILE`，可用于定位分图和计算耗时；诊断后关闭再测正常性能。[ORT 使用与诊断](https://github.com/spacemit-com/docs-ai/blob/main/zh/compute_stack/ai_compute_stack/onnxruntime.md)

现有项目记录的环境为 SpacemiT ORT 2.0.7、SpineRuntime 0.6.3；本地配套 ORT 头文件标记基础 ORT 为 `1.24.2+spacemit.a1`。厂商版本与基础 ORT 版本需分开记录，不应把主机的标准 onnxruntime 当成 K1 加速 runtime。

## 4. XSlim：官方文档与实际源码

核对的官方源码提交：`831b561e0e5db454e163062f8139ba4f56658bc0`（2026-10-14），`VERSION_NUMBER=2.1.2`；PyPI 也提供 2.1.2。它目前是候选环境，不是已经验证的本项目量化环境。[源码](https://github.com/spacemit-com/xslim/tree/831b561e0e5db454e163062f8139ba4f56658bc0)、[发布包](https://pypi.org/project/xslim/2.1.2/)

### 4.1 显式锁定 opset

当前配置文档表格描述未设置 opset 时保留原值，但核对源码发现 `MIN_ONNX_OPSET_VERSION=24`，`format_onnx_model()` 未收到显式目标时会将较低 opset 转到 24。因此必须设置 `model_parameters.opset=17`，量化之后再次检查。禁止靠手工改 `opset_import` 的数字伪造兼容。[配置文档](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/configuration.md)、[实际转换逻辑](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/src/xslim/onnx_graph_helper.py#L435)、[默认版本常量](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/src/xslim/defs.py#L96)

源码还显示 `sim_en` 控制日志，但同函数中的 `optimize_onnx_model()` 调用并未被其条件包围。因此不能仅凭 `skip_onnxsim` 就假定所有优化/融合关闭；以最终图为准。该结论只针对上述提交，不外推后续版本。[同一源码函数](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/src/xslim/onnx_graph_helper.py#L473)

### 4.2 九输出与自动解码融合

新 XSlim 可以把匹配的完整 YOLO 解码子图融合为 `spacemit_functions.YoloDecode`，并附带 FunctionProto。首条路线直接导出九个原始分支，不在 ONNX 中嵌入完整解码/NMS，避免依赖这一新融合路径。不得先验断言旧 runtime 一定支持或一定不支持；发现新增 domain 时应独立验证。`truncate_var_names` 只在确有需要时使用，不能照抄其他模型的张量名。[官方 YOLO 示例](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/examples.md#6-yolo-detection-with-automatic-decode-fusion)

### 4.3 量化配方

以静态 INT8 PTQ 为主。官方检测示例建议 `precision_level=1, finetune_level=2`，曾作为本项目默认候选；2026-10-19 起，主配置按 Gitee `spacemit-demo` YOLOv8 公开配方映射为 XSlim `p0/f3 + minmax + max_percentile=0.9995`，映射依据和边界见 [Gitee 对照记录](2026-10-19-gitee-yolov8-alignment.md)。p1/f2 仍保留为对照实验候选。precision_level 越大不表示越快，finetune_level 也不是训练 epochs。[官方示例](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/examples.md)、[调优指南](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/accuracy_tuning.md)

初始校准取 500 张真实部署分布图片，batch=1，不足时如实记录数量；每个输入尺寸独立生成校准输入。校准必须使用与部署相同的 letterbox、RGB、114 padding、1/255 和 NCHW。官方支持自定义 `script.py:function` 返回 batched torch.Tensor，可以复用同一预处理实现，不能套用 ImageNet center crop。[自定义预处理接口](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/configuration.md#custom-preprocessing)

官方调优指南允许从验证/测试分布准备校准数据。考虑本工程还会反复选择量化配方，我们采用训练子集或独立校准集，最终 test 保持独立。这是本工程的评估设计选择，不是 XSlim 强制要求。保留 Graphwise report，同时计算逐类 AP/召回；逐层数值误差不能代替任务指标。

静态量化输入应为 FP32 ONNX，不可将这三份已经 QDQ 量化的参考文件再次静态量化。[XSlim 输入约束](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/doc/configuration.md#static-quantization-input-requirements)

### 4.4 环境隔离

官方 2.1.2 的主机依赖包括 ONNX 1.21.x、onnxruntime 1.24.0–1.24.3、NumPy≥2、onnxslim=0.1.87。参考模型元数据里的旧 XSlim 2.0.6 则要求 ONNX 1.16.x、onnxruntime 1.20.x。二者不能混装进同一个环境；本轮检查工具使用的 ONNX 1.17.0 也不能充当它们的正式量化环境。[2.1.2 依赖](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/requirements.txt)、[2.0.6 发布元数据](https://pypi.org/pypi/xslim/2.0.6/json)

训练/导出、量化、K1 推理分别管理版本。训练框架先以官方模型元数据中的 Ultralytics 8.3.200 为候选基线，不直接追随 latest；PyTorch/CUDA/torchvision 必须按实际驱动选择并验证后锁定。不要无选择地安装 `ultralytics[export]` 的全部跨平台导出依赖。

## 5. 类别迁移的实际工作

保留 `[0-2][8-79]`、替换 `[3-7]` 是合理的配置方式，但应分清：

1. 保留编号：生成一致的类别表、数据映射和模型元数据。
2. 保留初始化：对照 checkpoint 结构迁移保留类别的分类头行，重置替换类行。
3. 保留能力：混入原类回放数据并做独立回归评估。

只执行前两步仍可能遗忘。新类图中未标出的原类还可能被当作背景。Ultralytics 官方微调说明也建议通过加入原类样本降低遗忘；冻结骨干只能作为辅助，不能作能力保证。[官方微调说明](https://docs.ultralytics.com/guides/finetuning-guide)

原 COCO JSON category_id 并非 0–79 连续编号，必须转换。custom_only 模式按类别表长度 N 建头，图像数量决定样本量，不决定类别数；训练仍可以使用预训练骨干。[检测数据格式](https://docs.ultralytics.com/datasets/detect/)

## 6. 额外注意事项与待验证项

- 颜色分类关闭 hue 扰动；白平衡和真实光照变化需要采集覆盖。增强设置应在逐类验证后调整。[增强定义](https://docs.ultralytics.com/guides/yolo-data-augmentation)
- 按采集组划分 train/val/test，排除跨集重复/近重复，保留真实背景负样本。
- 长方形导出不是改 YAML 尺寸即可完成；需要对应固定形状导出、校准、解码和准确率验证。训练框架是否真正按指定长方形训练也要检查，不能把 `rect=True` 当作固定 192×320 的保证。
- 现有 ROS 解码器多处写死 80，N 类模型需配套适配：引擎 shape 检查、分类循环、标签校验和部署配置。当前 `yolo` 调研未修改机器人源码。
- 下载文件须验证 HTTP 状态、体积、SHA-256 和实际解析；不能只检查文件是否存在。预训练权重、参考结构和数据来源要随产物记录。
- 分别记录冷启动、预热后推理 P50/P95、端到端图像年龄、CPU/RSS。相机 FPS 上限不等于模型能力上限；K3 数据不替代 K1 数据。
- 环境从零复用需要干净 Linux 安装验证，GPU/CPU 两种主机配置分别锁依赖，并记录网络镜像与 wheel 来源。当前只有检查环境跑通。
- 交付前核对各源码、预训练权重与数据集的许可，随下载清单记录来源和许可链接。Ultralytics 与 XSlim 的许可不能混为一谈。[Ultralytics 许可入口](https://www.ultralytics.com/license)、[XSlim 许可](https://github.com/spacemit-com/xslim/blob/831b561e0e5db454e163062f8139ba4f56658bc0/LICENSE)

尚待完成：高速结构训练来源定位；类别头迁移实现；N 类部署适配；训练/量化干净环境；真实标注数据；FP32/INT8 指标；K1 分图和性能验收。未验证项目不标为最优或已通过。

## 7. 本轮工具验证

在新的临时 Linux Python 3.10 虚拟环境中运行本项目 `scripts/setup_env.sh`，成功安装固定的检查依赖；随后通过 `scripts/inspect_models.sh` 重查三份模型，JSON 与保存的结构报告完全一致。另已核对 shell 语法、Python 语法、YAML 示例、80 类槽位分区和文档本地链接。

原始三份模型的最终 SHA-256 与初次读取一致。两份高速模型通过 ONNX checker；官方文件保留原始 metadata 重复导致的 FAIL，并单列内存去重诊断结果。本轮没有用该诊断替换模型文件，也没有新增模型精度或 K1 性能结论。
